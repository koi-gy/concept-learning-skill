概念学习资料：大模型的上下文（Context Window）

生成时间 2026-09-06 来源门槛 官方文档级 最后核查 ⬜ 未核查 状态 AI 草稿 · 待人工核查与改写
TL;DR — 30 秒版
  • 上下文窗口 = LLM 在一次请求里能"看见"的所有 token，包括系统提示、对话历史、工具结果、生成的输出。
  • 它是模型的工作记忆，不是训练数据。
  • 窗口越大≠越好：随着 token 增加，准确率和召回会下降（Anthropic 称之为 context rot）。
  • 输出、extended thinking（推理过程）、工具定义都消耗上下文。
  • 管好上下文比堆大窗口更重要——长文档场景的提示工程有专门技巧。

1. 这是什么

上下文窗口（context window）这个词在不同来源里指代很一致，但侧重点不同：

  • Anthropic（docs.anthropic.com）："the text a language model can reference when generating a response, including the response itself"——一句话回答"是什么"，并强调它是模型的 working memory，不是训练语料。
  • Anthropic（long context 提示工程博客）：从提示工程角度，给出 Claude 100k / 200k 长上下文场景下"如何提高召回"的技巧（参考引文、Few-shot 示例）。

没有显著冲突，这两个来源互相补充：官方文档给定义和计数规则，提示工程博客给实践技巧。

2. 我的理解

这一段是 AI 草稿，必须由你用自己的话改写。

如果让我给同学讲，我会这样说——

"你可以把 LLM 想成一个人在做听力考试。听力材料就是上下文窗口——他只能在听力材料里听到的内容里找答案。考试时间（窗口大小）不是越长越好：第一，听力材料太长，他容易走神、抓不住重点；第二，他一边听一边要在脑子里复述和推理（这就是 extended thinking），这些'思考'也会占用他的精力。所以好的提示不是塞更多东西进去，而是把最相关的几段放进去。"

关键的认知是：上下文不是数据库，是注意力。放进去的东西越多，模型对每一条的注意力越分散。这是为什么"长上下文不等于好用"。

3. 核心机制 / 组成

3.1 哪些东西算上下文

来自 Anthropic 官方文档的明确列表：

  1. 系统提示（system prompt）
  2. messages 数组里的每一条消息（包括图片、PDF、文档）
  3. 工具定义（tool definitions）
  4. 模型生成的输出（包括 extended thinking 的思考 token）
  5. 如果用 prompt caching：cache_read / cache_creation 都算

它和别的组件怎么连：每次 API 请求的 usage 字段会返回这次请求消耗的 token 数，是判断"还剩多少窗口"的唯一可靠方式。

3.2 长上下文的衰减（Context Rot）

Anthropic 在 2024-09 的 long context 提示工程博客里给了一个量化结论：

"As token count grows, accuracy and recall degrade, a phenomenon known as context rot."

他们的实验发现，长文档里有用的细节越多，模型对任意单个细节的召回越差——这就是 context rot。即使窗口扩大到 1M token，也不是"装得下就找得到"。

3.3 长上下文提示工程技巧

同样来自 Anthropic 的官方提示工程指南（适用于 20k+ token 的输入）：

  • 长文档放顶部，查询放最后——查询放最后可让响应质量提升最多 30%。
  • 用 XML 标签结构化文档——多个文档时给每个包上 <document> 标签和元数据。
  • 先让模型引用原文——"先引用文档中相关的部分，再执行任务"，帮助模型聚焦。

4. 一个具体应用场景

长文档问答（Long-Document QA）——把一本几百页的技术手册或合规文档塞进上下文，让模型回答问题。

  • 谁在用：法律科技公司（如用于合同审查）、企业知识库、客服 agent。
  • 解决什么问题：人工读几百页文档耗时；传统 RAG 检索可能漏掉关键段落。
  • 流程：把文档放进上下文 + 用"先引用再回答"的提示模板 + 设置引用证据。
  • 关键效果：Anthropic 的实验显示，用"先提取相关引文再回答"的技术能让长上下文召回显著提升（具体提升百分比见官方博客）。

为什么这个例子可信：Anthropic 官方用"政府会议记录"（一份长文档）做过量化实验，方法、数据、prompt 模板都公开。

5. 边界 & 容易混淆的点

容易混的概念区别
Context Window vs 训练数据 训练数据是模型"知识"的来源；上下文窗口是单次请求里能"看到"的内容。两者量级、用法、计费都不同。
Context Window vs RAG 上下文窗口是 LLM 的"工作记忆"容量；RAG 是"用检索的方式把相关片段放进上下文"的技术。RAG 可以看作填满窗口的策略，不是替代品。
输入 token vs 输出 token 窗口同时包含两者；输出（包括 thinking）也消耗窗口。Anthropic 明确说"生成 output 也是上下文的一部分"。
Window 大小 vs 有效注意力 1M token 不等于"记得住 1M token"。context rot 意味着放在头尾的信息比放中间的更容易被记住。

常见误区：

  • "窗口越大越好"——错。窗口大只代表能装下，不代表每条都找得到。
  • "把所有文档塞进去就不需要 RAG 了"——错。RAG + 精准检索通常比"全塞进去"效果更好、成本更低。
  • "extended thinking 是免费的"——错。thinking token 也算上下文，也算费用。
